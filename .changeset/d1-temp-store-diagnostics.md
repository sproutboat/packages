Embedded SQLite no longer needs a temporary file, and a runaway sort cannot take the worker down. A worker may create files only under its data directory, so a sort, temporary table or statement journal that outgrew the page cache failed with `unable to open database file` (SQLITE_CANTOPEN) when SQLite tried `/var/tmp` or `/tmp`. Every connection now sets `temp_store=MEMORY` (and statement journals stay in memory, even if the app sets `temp_store=FILE`). Those sorts and temporary tables live in RAM, so SQLite also gets a hard heap limit (`sqlite3_hard_heap_limit64`): a quarter of the app's memory limit (8 MiB at 32 MiB, never under 4 MiB; 256 MiB when no limit is set, as in a standalone binary). A statement that needs more fails with `out of memory` (SQLITE_NOMEM) and the worker keeps serving, where before it would have grown until the cgroup killed it and every request in flight with it. Cloudflare's workerd sets the same kind of limit for D1 (`sqlite3_hard_heap_limit64`, next to a 128 MiB soft limit).

Failures that remain name their file: a failed `open(2)` of the database, its `-wal`, `-shm` or a temporary file, and a statement that ends in CANTOPEN or an I/O error, write one rate-limited line to stderr (`sproutd-sqlite: app=ID open:rw+creat errno=13 (Permission denied) file=$DATA/d1/app.sqlite-wal`), without SQL text or row data. A path under the app's data directory is shown as `$DATA/…` (whether the state directory is a symlink or not), any other path as `<outside>/NAME`, and `errno=-` means the failing call set none.
